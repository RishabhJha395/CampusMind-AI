1. Project Overview & Problem Statement

1.1 The Problem

University students face a fragmented information landscape. Critical data — examination schedules, academic ordinances, fee structures, hostel notices, departmental circulars, faculty contacts, scholarship deadlines — is scattered across dozens of sub-pages, PDFs, and notice boards of poorly-maintained institutional websites. These sites are notoriously:

  • Slow and unreliable: Static HTML pages often rendered by outdated CMSes.
  • Non-searchable: Google cannot index dynamically-rendered JavaScript pages. Internal site searches are rudimentary keyword matchers.
  • Inconsistent: Older announcements contradict newer ones. PDF ordinances from 2021 and 2025 may coexist with conflicting rules.
  • Inaccessible to natural language: A student cannot ask "What is the minimum attendance for a backlog student?" and receive a precise, cited answer.

The manual cost of navigating these systems is high: students lose hours weekly searching for authoritative answers, often settling for unreliable peer advice.

1.2 The Solution: CampusMind AI

CampusMind AI is a multi-tenant, university-specific Retrieval-Augmented Generation (RAG) knowledge platform. It transforms the unstructured, fragmented data of a university's digital presence into a conversational, citation-backed AI assistant.

The system operates through three distinct lifecycle phases:

Phase Description
Ingestion An automated pipeline crawls the university's entire web presence (JS-rendered pages + PDFs), processes and chunks the content, generates semantic embeddings, and indexes everything into a vector database.
Retrieval When a user asks a question, the system performs a sophisticated hybrid search — combining semantic vector search with exact full-text keyword search — then merges results using Reciprocal Rank Fusion and reranks them with a Cross-Encoder model.
Generation The top-ranked context chunks are injected into a structured prompt, and Google Gemini 2.5 Flash generates a precise, grounded answer with zero tolerance for hallucination.

1.3 Core Value Proposition

  • Accuracy over Creativity: The LLM is instructed with CRITICAL RULES in the system prompt to never hallucinate and to explicitly refuse if context is insufficient.
  • Always Fresh: A GitHub Actions CI/CD pipeline re-crawls university notice boards every 6 hours automatically, ensuring the knowledge base stays current without any manual intervention.
  • Multi-tenant by Design: The system's university_id model allows a single deployed instance to serve multiple universities, each with its own isolated Qdrant collection, configuration, and branding.
  • Cost-Efficient: Using a locally-run embedding model eliminates per-token embedding API costs — crucial for a high-volume ingestion pipeline that processes thousands of chunks per run.

4. Core Component Deep Dives

4.1 Reciprocal Rank Fusion (RRF) — The Hybrid Search Merger

The Problem with Single-Method Retrieval

Pure cosine similarity (vector search) is excellent at finding semantically similar content — it understands that "attendance rules" and "presence requirements" are related concepts. However, it fails on exact terminology — if a student asks "What is DTU ordinance 5.3?", a vector model may return loosely related content instead of the exact clause.

Pure keyword search (BFS text match) is the opposite — it is precise for exact terms but fails on paraphrasing and synonyms.

What RRF Does

RRF was introduced by Cormack et al. (2009) as a method to merge multiple ranked lists without needing scores to be comparable across systems. The formula is:

$$\text{RRF_Score}(d) = \sum_{i=1}^{n} \frac{1}{k + \text{rank}_i(d)}$$

Where: - $d$ is a document/chunk - $n$ is the number of ranked lists being merged (in this system: 4 dense + 1 keyword = 5 lists) - $\text{rank}_i(d)$ is the 0-indexed rank of document $d$ in list $i$ (0 = top result) - $k = 60$ is a smoothing constant that prevents rank 1 from dominating too heavily

The Actual Implementation

From orchestrator.py (lines 27–56):

```python def _reciprocal_rank_fusion(self, search_results_lists: List[List[VectorResult]], k: int = 60) -> List[VectorResult]: fused_scores = {} payload_map = {}

for results in search_results_lists:
    for rank, doc in enumerate(results):
        doc_id = doc.id
        if doc_id not in fused_scores:
            fused_scores[doc_id] = 0.0
            payload_map[doc_id] = doc.payload

        # RRF Formula: 1 / (k + rank)
        fused_scores[doc_id] += 1.0 / (k + rank)

sorted_ids = sorted(fused_scores.keys(), key=lambda x: fused_scores[x], reverse=True)
...

```

Why $k=60$? This is the empirically established default from the original RRF paper. It provides a good balance: the top-ranked document in any single list receives score $\frac{1}{60+0} = 0.0167$, while rank 10 receives $\frac{1}{70} = 0.0143$. The difference is meaningful but not overwhelming, so a document appearing at rank 5 in two different lists scores higher than one appearing at rank 1 in only one list. This is the core intuition — consensus across retrieval methods is more valuable than dominance in a single method.

Why RRF Beats Cosine-Only in This System

  1. Query Expansion amplifies it: The system generates 4 query variations. Each variation produces its own dense search result list. A chunk consistently appearing in top results across all 4 query framings gets a very high RRF score — a strong signal of genuine relevance. This is impossible with a single cosine search.

  2. Exact terminology safety net: An exam schedule page that contains the exact string "End Semester Examination 2025-26" will be captured by the keyword search arm even if the query was phrased as "when are finals?" The RRF fusion ensures it still surfaces in the final ranked list.

  3. Score normalization: Cosine similarity scores (0.0–1.0) and keyword match scores (assigned a flat 1.0) are not comparable. RRF uses only rank positions, so it is scale-invariant — no score normalization is needed.

4.2 The Incremental Indexing Cache (hash_store.json)

The Problem It Solves

Running a full re-ingestion of a university website every 6 hours would be extremely wasteful. The DTU website has thousands of pages. Most content (faculty lists, department pages, old notices) changes at most once a semester. Re-embedding and re-inserting identical content every 6 hours wastes: - Compute time on the GitHub Actions runner (free tier has limited minutes) - Unnecessary upsert operations to Qdrant Cloud

How the HashStore Works

The HashStore class (ingestion/indexing/hash_store.py) is a simple but powerful incremental processing gate. Its core is a JSON dictionary mapping {url: sha256_hash_of_content}.

The lifecycle during a pipeline run:

``` ┌─────────────────────────────────────────────────┐ │ hash_store.json (persisted via GitHub Actions │ │ cache between runs) │ │ { │ │ "https://dtu.ac.in/notice/1.html": "a3f2...", │ │ "https://dtu.ac.in/notice/2.html": "b1c9..." │ │ } │ └───────────────────────────┬─────────────────────┘ │ Load on startup ▼ For each crawled document: new_hash = SHA256(document.content) old_hash = store.get(url)

if old_hash == new_hash: → SKIP (skipped_docs++) else: → Delete old Qdrant vectors for this URL → Chunk → Embed → Upsert new vectors → Update store[url] = new_hash → Every 50 docs: save to disk (checkpoint)

On full tier only: deleted_urls = all_stored_urls - seen_urls → Delete vectors for orphaned URLs from Qdrant → Remove from store

Final save → hash_store.json ```

The GitHub Actions Cache Layer

The critical mechanism that makes this stateful across runs is the GitHub Actions cache:

```yaml

From incremental-indexing.yml lines 44–48

  • name: Restore HashStore Cache uses: actions/cache@v4 with: path: hash_store.json key: hash-store-${{ github.ref }}

Lines 79–84

  • name: Save HashStore Cache uses: actions/cache/save@v4 if: always() # Save even if the run partially fails with: path: hash_store.json key: hash-store-${{ github.ref }}-${{ github.run_id }} ```

The restore uses a branch-level key (hash-store-main), and the save includes a run_id suffix. This is a standard GitHub Actions pattern for rolling cache updates: the restore step finds the most recent cache matching the key prefix (hash-store-main-*), and the save step creates a new cache entry for this run, ensuring the next run picks up the latest state.

Result: On a 6-hour fast-tier run, if only 3 new notices were posted, the pipeline skips ~97% of crawled pages and only upserts ~30–100 new chunks. This is the difference between a 30-minute run and a 3-minute run.

4.3 Playwright vs. requests + BeautifulSoup — Dynamic JavaScript Rendering

Why Static HTTP Clients Fail for University Sites

Modern institutional websites often use: - React / Angular / Vue SPAs where the initial HTML is a nearly empty <div id="root">. The actual content is injected by JavaScript after the browser loads and executes scripts. - AJAX-fetched notice tables where a JavaScript function fires a fetch() call to an API endpoint and injects HTML into the DOM after the initial page load. - Server-Side Rendering with client-side hydration — the HTML contains data, but navigation and filtering are JavaScript-driven.

A standard requests.get(url) call retrieves the raw HTML before any JavaScript executes. BeautifulSoup parsing this HTML would find an empty shell with no useful content.

How Crawl4AI + Playwright Solves This

Crawl4AI uses Playwright internally to launch a real Chromium browser instance. The call:

```python

From web_crawler.py line 81

result = await crawler.arun(url=url) ```

Does the following under the hood: 1. Opens the URL in a Chromium browser tab. 2. Waits for the page's JavaScript to execute (network idle strategy). 3. Waits for dynamic content to be injected into the DOM. 4. Reads the final rendered DOM — the complete HTML as a human sees it. 5. Converts the rendered HTML to clean Markdown (stored in result.markdown), stripping navigation menus, footers, scripts, and styles.

The result is clean, structured text ready for chunking — no custom HTML parser needed. The GitHub Actions workflow installs Playwright Chromium: yaml python -m playwright install chromium

The BFS Crawler Architecture

The WebCrawler.extract() method implements Breadth-First Search crawling: - It maintains a queue of (url, depth) tuples and a visited set. - _is_valid_url() restricts crawling to the base domain (e.g., only pages on dtu.ac.in), preventing the crawler from following external links. - PDF links are intercepted and added to discovered_pdfs set instead of being crawled as HTML pages. - The crawler respects max_depth and max_pages limits, making it controllable and preventing runaway crawls.

The PDF Processing Path

When PDFs are encountered, the PDFConnector → PDFProcessor pipeline handles them: 1. httpx.AsyncClient downloads the PDF to a tempfile.TemporaryDirectory() — ensuring no disk clutter. 2. PyMuPDF attempts direct text extraction (fast, for digitally-created PDFs). 3. Tesseract OCR (pytesseract) is used as a fallback for scanned image-based PDFs. 4. The text is yielded as a Document with doc_type="pdf", processed through the same HashStore → Chunker → Embedder → Qdrant pipeline as web pages.

Priority sorting of PDFs before processing ensures resources are allocated to the most relevant content first: python def sort_key(url): if "2026" in u: return 0 # Current year notices first if "2025" in u: return 1 if "ordinance" in u or "rule" in u: return 2 # Academic regulations return 3

4.4 Query Expansion — The Hidden Multiplier

Before any search occurs, QueryExpansionService.expand_query() sends the user's original query to Gemini and asks it to generate 3 alternative phrasings using different vocabulary:

```python

From query_expansion.py

prompt = """Generate 3 alternative search queries that mean the exact same thing but use different vocabulary, synonyms, or official terminology (e.g. "syllabus" -> "scheme of teaching", "schedule" -> "timeline").""" ```

If a student asks "What are the attendance rules?", the expander might generate: - "minimum attendance percentage requirement" - "presence policy for lectures and practicals" - "condonation of shortage of attendance criteria"

Each of these 4 queries (original + 3 variations) is independently embedded and used in dense search. This dramatically increases the probability of finding the relevant chunk regardless of how its author worded it.

4.5 The Deterministic UUID Strategy for Chunks

This is a subtle but important implementation detail in TextChunker.chunk_document():

python content_hash = self._generate_hash(text) # SHA-256 of chunk text namespace = uuid.NAMESPACE_URL deterministic_id = str(uuid.uuid5(namespace, content_hash))

Each chunk's ID is a UUID v5 (namespace UUID + SHA-256 hash). This means the same text always produces the same UUID. The consequence: if a page's content doesn't change and a re-ingestion occurs (bypassing the HashStore check, e.g., in a corrupted state), the Qdrant upsert call will simply overwrite the same point ID with identical data — it is idempotent. No duplicates are ever created.

5. Scalability & System Limitations

5.1 Current Bottlenecks

Bottleneck 1: Single-Threaded Crawl per Run

The current crawler processes URLs sequentially in a BFS loop. While Crawl4AI is async internally, the pipeline processes one document at a time before moving to the next. At 2000 pages per full run, this is the primary time constraint.

Bottleneck 2: Embedding is CPU-Bound on the Runner

Running SentenceTransformer on a GitHub Actions ubuntu-latest runner (2-core CPU, 7GB RAM) is functional but slow. Batched inference helps, but embedding 10,000 chunks per run is still CPU-intensive.

Bottleneck 3: lru_cache on Singleton Services

The get_embedder() and get_rag_service() functions use Python's @lru_cache. This works correctly for a single-process deployment on Render, but breaks down if the server is scaled horizontally to multiple instances. Each instance would load its own copy of the SentenceTransformer model, and there is no shared state.

Bottleneck 4: Synchronous Qdrant Client Calls

The QdrantStore uses the synchronous Qdrant Python client (client.query_points(), client.scroll()). These are blocking calls inside async FastAPI handlers, which violates ASGI principles and creates a head-of-line blocking problem under high concurrency. The fix would be to use asyncio.to_thread() or the async Qdrant client.

Bottleneck 5: hash_store.json is a Flat File

At ~5,800 URLs (current size is 94KB), the flat JSON file is fine. At 100 universities with 20,000 URLs each (2,000,000 entries), it becomes a bottleneck to load, diff, and save. The file would be hundreds of megabytes.

5.2 Scaling to 100 Universities & 100,000 Students

Architecture Change 1: Message Queue for Crawling (Kafka / RabbitMQ)

Current: A single GitHub Actions runner processes one university sequentially.

Scaled: A Kafka topic crawl-jobs receives one message per university per tier. Multiple crawler worker pods (running in Kubernetes) consume from this topic in parallel. Each pod handles one university's crawl, batches discovered URLs, and publishes embed-jobs to a downstream topic. An embedding-worker service consumes these, runs batched embedding, and publishes index-jobs to an indexer-worker that upserts to Qdrant.

GitHub Actions (trigger only) ↓ Kafka: crawl-jobs ┌──────────┬──────────┬──────────┐ ▼ ▼ ▼ ▼ Crawler Crawler Crawler Crawler Worker 1 Worker 2 Worker 3 Worker N └──────────┴──────────┴──────────┘ ↓ Kafka: embed-jobs ↓ Embedding Workers (GPU-backed) ↓ Kafka: index-jobs ↓ Qdrant Distributed Cluster

Architecture Change 2: GPU-Backed Embedding Service

Replace CPU-based SentenceTransformer inference on GitHub Actions runners with a dedicated embedding microservice running on GPU hardware (AWS g4dn.xlarge or Google Cloud n1-standard-4 with T4). A single T4 GPU can embed ~100,000 sentences per second vs. ~1,000/second on a CPU. The service exposes a gRPC endpoint: EmbedBatch(texts: [str]) -> vectors: [[float]].

Architecture Change 3: Horizontal Scaling of the FastAPI Backend

  • Replace Render single-instance with Kubernetes Deployment behind an NGINX Ingress Controller or AWS Application Load Balancer.
  • Each pod loads the SentenceTransformer model — this is memory-heavy (~500MB per pod). The fix is to route embedding requests to the external GPU embedding service instead of loading the model locally in each pod.
  • Use Redis for rate limiting state (replacing the in-process slowapi limiter which does not share state across pods).

Architecture Change 4: Qdrant Distributed Cluster

Replace Qdrant Cloud's single-node free tier with a Qdrant distributed cluster with sharding: - Each university collection is sharded across multiple nodes. - Read replicas handle query traffic; write replicas handle ingestion upserts. - Use Qdrant's built-in replication factor of 2 for high availability.

Replace the flat hash_store.json file with a Redis hash map (HSET university:dtu:url_hashes <url> <sha256>) or a PostgreSQL table:

This enables: - Concurrent writes from multiple crawlers (no file lock contention). - Efficient orphan detection via WHERE last_seen_at < current_run_timestamp. - Historical hash tracking.

Qdrant handles this well, but the alternative is a single shared collection with university_id as a required payload filter on every query. The current per-collection approach is actually the correct multi-tenant design for isolation and access control — it scales to hundreds of universities without architectural changes.

6. Top 10 Technical Interview Questions & Answers

Q1: "Why did you use RRF instead of just taking the top results from a single vector search? Isn't cosine similarity already semantic?"

Ideal Answer:

Cosine similarity is excellent for semantic proximity but has two critical weaknesses in a production RAG system. First, it can miss exact terminology — a notice containing "ordinance 5.3(a)" might not score well against a query vector for "attendance rules" even if they're semantically related. Second, it's sensitive to how a query is phrased — slight rewording can change the top-10 results significantly.

I address both by running a 5-way hybrid search: 4 dense vector searches (one per LLM-generated query variation) and 1 exact keyword text search using Qdrant's MatchText filter. RRF then merges these 5 ranked lists using the formula score += 1/(60 + rank) for each list a document appears in.

The key insight of RRF is that it uses only rank positions, not raw scores. This makes it scale-invariant — cosine scores (0–1) and keyword match scores (1.0 flat) are not comparable numbers, but their rank positions are. A document that consistently appears in the top-10 of multiple independent searches gets a high RRF score — and that consistency is a strong signal of genuine relevance. This is provably better than any single-list approach for heterogeneous retrieval.

Q2: "Your system prompt says 'ABSOLUTELY NO HALLUCINATION.' How do you technically enforce this? The LLM can still ignore instructions."

Ideal Answer:

You're right that we can't cryptographically prevent hallucination — it's a probabilistic model. However, I apply three layers of defense:

Layer 1 — Architectural: The system is RAG-grounded. The LLM only sees the retrieved context chunks, not a broad general prompt. It literally cannot answer a question about "DTU exam schedule" from pre-training knowledge if the system prompt fills all the context with retrieved chunks.

Layer 2 — Prompt Engineering: The system prompt contains explicit, unconditional rules: 1. "ABSOLUTELY NO HALLUCINATION. Never invent, guess, or pull information from pre-trained knowledge." 2. "If the question cannot be answered from CONTEXT, reply exactly: 'I don't have enough information about that right now.'" 3. "If context contains conflicting information, mention both and state where they were found."

The temperature is also set to 0.3 — low temperature reduces creative generation and keeps the model closer to the distribution of its input context.

Layer 3 — Model Choice: Gemini 2.5 Flash is a model trained with strong instruction-following. Combined with low temperature and a highly structured system prompt, the practical hallucination rate is very low.

The remaining risk is context stuffing — if 20 chunks are retrieved but none actually answers the question, the model might extrapolate. This is why the explicit refusal instruction in Rule #2 is critical.

Q3: "You mentioned @lru_cache on your dependency injection functions. What problem does this solve and what does it break?"

Ideal Answer:

@lru_cache on get_embedder() and get_rag_service() ensures that expensive initialization — loading a 500MB SentenceTransformer model into memory — happens exactly once per process lifetime, no matter how many HTTP requests hit the server. Without it, every API request would re-instantiate the model from disk, which would be catastrophically slow (~5–10 seconds per request).

However, it has a critical limitation: it only works correctly in a single-process deployment. If I horizontally scale to 4 FastAPI pods, each pod has its own process with its own lru_cache instance. Each pod loads its own copy of the model — 4 × 500MB = 2GB of RAM wasted on model copies. There's no shared memory between processes in standard Python.

The correct solution at scale is to extract the embedding functionality into a dedicated embedding microservice — a separate process (or pod) that loads the model once and serves embedding requests via gRPC or HTTP. The FastAPI pods then become stateless and can be scaled freely.

Additionally, @lru_cache has no TTL — if I update the Qdrant URL or API key via environment variable changes, the old cached QdrantStore instance persists until the process restarts.

Q4: "Walk me through the exact data flow from a user typing a question to receiving an answer."

Ideal Answer:

  1. Frontend posts {university_id: "dtu", query: "attendance rules", stream: true} to POST /api/v1/chat.
  2. FastAPI middleware assigns a request_id UUID, checks the rate limit (30 req/min per IP via slowapi), and passes the request down.
  3. Dependency injection provides the singleton RAGService instance.
  4. RAGService.retrieve_context() is called:
  5. QueryExpansionService.expand_query() calls Gemini to generate 3 alternative phrasings → 4 total queries.
  6. For each of the 4 queries, LocalEmbedder.embed_query() produces a 384-dim vector.
  7. QdrantStore.search() runs ANN cosine search, retrieving top-40 results per query → 4 dense result lists.
  8. QdrantStore.text_search() runs MatchText keyword filter on original query → 1 keyword result list.
  9. _reciprocal_rank_fusion() merges all 5 lists using score += 1/(60+rank) per document per list, returns top-40 by fused score.
  10. CrossEncoderReranker.rerank() scores each of the 40 (query, chunk_text) pairs using ms-marco-MiniLM-L-6-v2, sorts, returns top-20.
  11. RAGService.chat_stream() builds the system prompt with 20 context chunks and sends to OpenRouterService.generate_response_stream().
  12. The service calls openrouter.ai/api/v1/chat/completions with stream: true using httpx.AsyncClient.send(req, stream=True).
  13. FastAPI's StreamingResponse reads chunks from the aiter_lines() async generator, parsing SSE events, and forwards them to the browser.
  14. The React frontend listens to the SSE stream, first receiving a {type: "sources", data: [...]} event (displaying citation links), then {type: "chunk", content: "..."} events that append text to the UI in real-time.

Q5: "What happens if Qdrant Cloud goes down during a user query?"

Ideal Answer:

Currently, the failure mode is a 500 error. The QdrantStore.search() method has a try/except that logs the error and returns an empty list []. The RAG orchestrator would then call the LLM with zero context chunks, resulting in the LLM refusing to answer per its system prompt rules — the user gets "I don't have enough information about that right now."

This is actually a safe failure mode — the user gets an honest refusal rather than a hallucinated answer. However, the 500 HTTP response from the FastAPI layer is not ideal for the frontend.

Improvements I would make: 1. Circuit breaker pattern — after N consecutive Qdrant failures, fast-fail all requests for a cooldown period rather than hammering a down service. 2. Health check endpoint — /api/v1/health already checks vector_store.check_health() (a get_collections() call). A load balancer health check on this endpoint would route traffic away from a pod with a broken Qdrant connection. 3. Graceful degradation — return a specific error message to the frontend: "The knowledge base is temporarily unavailable. Please try again in a few minutes." with a 503 status.

Q6: "Why do you use Server-Sent Events (SSE) for streaming instead of WebSockets?"

Ideal Answer:

SSE and WebSockets both enable server-push communication, but they have fundamentally different characteristics:

SSE WebSockets
Direction Server → Client (unidirectional) Bidirectional
Protocol HTTP/1.1 or HTTP/2 WebSocket protocol (ws://)
Complexity Simple — just HTTP with text/event-stream content type Requires upgrade handshake, custom server management
Reconnection Automatic browser reconnect built-in Must implement manually
Proxy/CDN Works through standard HTTP proxies May require specific proxy configuration

For a chat use case, the user sends one query (HTTP POST) and receives a streaming text response. This is purely unidirectional server-push after the initial POST — exactly what SSE was designed for. There is no need for the client to push data during the stream. WebSockets would add unnecessary complexity.

In the implementation, StreamingResponse(rag_service.chat_stream(...), media_type="text/event-stream") leverages FastAPI's native support. The chat_stream() method yields properly formatted SSE messages (data: {...}\n\n) directly as an async generator, which FastAPI streams to the client with zero buffering. This integrates cleanly with Vercel's edge infrastructure.

Q7: "Your TextChunker uses a sliding window with word-boundary splitting. What's the limitation of this approach, and what would a production-grade chunker do differently?"

Ideal Answer:

The current chunker (_sliding_window_split) is a word-count-based sliding window that splits text when the character count exceeds chunk_size=1000. The chunk_overlap=200 backtrack ensures context continuity across chunk boundaries.

Limitations:

  1. Semantically agnostic: It can split a paragraph mid-sentence, or cut through a list item, destroying the semantic coherence of a chunk. The chunk boundary is determined purely by character count, not meaning.

  2. Ignores document structure: A page might have H1 headings, tables, and bullet lists. The chunker treats all of this as flat text. A chunk might start mid-table or contain a heading followed by content from a different section.

  3. No metadata enrichment: Chunks don't inherit contextual information about where they appear in the document (e.g., "this chunk came from the section titled 'Examination Rules'").

Production improvements:

  1. Semantic chunking: Use sentence-boundary-aware splitting. Libraries like langchain.text_splitter.RecursiveCharacterTextSplitter with separators=["\n\n", "\n", ". "] are more semantically aware. More advanced approaches use a sentence embedding model to group semantically related sentences together.

  2. Markdown-structure-aware chunking: Since Crawl4AI returns Markdown, parse it to identify #, ## headings. Each major section becomes a chunk with the heading text prepended as context ("## Examination Policy\n\n<text>"). This is called contextual chunking.

  3. Late chunking / proposition splitting: Newer approaches (e.g., chonkie library) split text into individual propositions/facts rather than fixed-length windows, improving retrieval precision significantly.

Q8: "What is Scalar INT8 Quantization in Qdrant and why did you enable it?"

Ideal Answer:

Vector quantization is a technique to compress floating-point vectors into a lower-precision representation. In the Qdrant configuration:

python quantization_config=models.ScalarQuantization( scalar=models.ScalarQuantizationConfig( type=models.ScalarType.INT8, quantile=0.99, always_ram=True ) )

What it does: Original vectors are float32 (32 bits per dimension). INT8 quantization maps each float32 value to an int8 value (8 bits) by calibrating the range based on the 99th percentile of observed values (quantile=0.99). This means:

  • Memory reduction: 32-bit → 8-bit = 4× smaller vectors. For 384-dimensional vectors: 384 × 4 bytes = 1.5KB per vector → 384 × 1 byte = 384 bytes per vector. At 100,000 vectors, that's 150MB → 37.5MB.
  • Speed improvement: Smaller vectors fit better in CPU cache. SIMD operations on INT8 are faster than on FLOAT32.
  • Trade-off: A small accuracy loss (~0.5–1% drop in recall). The quantile=0.99 means outlier values (top 1%) are clipped, which is an acceptable trade-off for the massive memory savings.
  • always_ram=True: Keeps the quantized vectors in RAM (not memory-mapped from disk), ensuring consistently fast ANN search latency.

This was specifically chosen because the project uses Qdrant Cloud's free tier, which has RAM constraints. Without quantization, the collection would overflow the free tier at ~100,000 vectors.

Q9: "If a notice gets deleted from the university website, how does your system detect and remove it from Qdrant?"

Ideal Answer:

This is handled by the full-tier run every Sunday midnight, using the HashStore.get_deleted_urls() method.

The logic is elegant: the HashStore tracks two sets during a crawl run: 1. self.store — all URLs that have been indexed (ever seen and processed). 2. self.seen_urls — all URLs encountered in the current crawl run.

python def get_deleted_urls(self) -> List[str]: all_stored_urls = set(self.store.keys()) deleted_urls = all_stored_urls - self.seen_urls return list(deleted_urls)

Any URL in store but not in seen_urls means the page was not reachable during the current full crawl — it was either deleted, redirected, or blocked. These are "orphaned" URLs.

In main.py (lines 168–183): python if tier == "full": deleted_urls = hash_store.get_deleted_urls() for url in deleted_urls: vector_store.client.delete( collection_name=collection_name, points_selector=models.Filter( must=[models.FieldCondition(key="source_url", match=models.MatchValue(value=url))] ) ) hash_store.remove_url(url)

All Qdrant vectors with payload.source_url == deleted_url are deleted, and the URL is removed from the store.

Why only on full tier? Fast-tier runs only crawl the notice board, not the entire site. A page not found during a fast run might simply not have been in the crawl scope — it can't be assumed deleted. Only a complete full crawl has the coverage to make a reliable determination that a page is truly gone.

Q10: "Your system is currently deployed on Render's free tier. What specific problems will you hit if traffic spikes to 1,000 concurrent users?"

Ideal Answer:

Several failure modes would manifest simultaneously:

1. Render Free Tier Sleep: Render free tier instances spin down after 15 minutes of inactivity. A cold start requires loading the SentenceTransformer model (~500MB) into memory, which takes 5–10 seconds. The first user after a sleep would experience a timeout.

2. Rate Limiter Becomes a Bottleneck: The slowapi rate limiter with default_limits=["30/minute"] is in-process. At 1,000 concurrent users, even if we don't hit the 30/min limit, the limiter's get_remote_address function call adds per-request overhead. More critically, if we scale to multiple instances, the in-process limiter state is not shared — each instance allows 30/min, effectively multiplying the limit by the number of instances.

3. Synchronous Qdrant Client Blocks the Event Loop: As mentioned, QdrantStore.search() uses the synchronous Qdrant client, which makes blocking I/O calls inside an async handler. Under 1,000 concurrent users, this means hundreds of async event loop iterations are blocked waiting for Qdrant responses, destroying the throughput benefit of async Python.

4. Per-Pod Model Loading at Scale: If we scale to 4 pods to handle load, each pod loads a 500MB model — 2GB of RAM just for model weights. On Render's paid tier (512MB–2GB per instance), this is prohibitively expensive.

5. OpenRouter Rate Limits: OpenRouter imposes per-key rate limits. At 1,000 users, each triggering a query expansion (1 LLM call) + generation (1 LLM call) = 2,000 LLM requests, this will hit rate limits quickly.

Solutions: - Move to Render's paid tier or to a proper K8s deployment. - Replace sync Qdrant client with async client (or asyncio.to_thread wrappers). - Extract embedding model to a dedicated service. - Use multiple OpenRouter API keys with round-robin routing. - Redis-backed distributed rate limiting.
